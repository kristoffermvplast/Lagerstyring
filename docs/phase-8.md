# Phase 8 — Receiving

Continues from main `7fb6925`; Phase 9 is not started. Hosted photos remain disabled.

## Scope and design

The receiving screen records one stock item per receipt: actual quantity in its stock unit, optional expected quantity, supplier, stock owner, storage location, pallet count, reference and comment. Item defaults suggest supplier/location; the stock unit is displayed. Confirmation explains the physical increase and discrepancy. Pallet count is informational; no handling units are created.

`GET/POST /api/companies/:companyId/receipts` and `GET .../receipts/:id` go through NestJS. Read requires `inventory.read`; posting also requires the new `inventory.receive`. Interactive selectors additionally need `masterdata.read`. Receiving permission does not grant corrections or reversals. Administrators retain their existing all-permission behavior; other roles must be explicitly granted receiving permission.

A receipt is an immutable `inventory_entries.kind=receipt` header with exactly one inventory line. The migration adds typed supplier/expected quantity/pallet count/comment/time/supplier-snapshot columns and tenant foreign keys, constraints, indexes and limited INSERT grants. No duplicate stock table or alternate writer is introduced. The existing owner/item/location/unit snapshots and atomic balance trigger remain authoritative. Supplier name/code and received time are generated by the database, not supplied by the client.

Difference is actual minus expected, using exact decimal arithmetic (8 fractional places). Unknown expectation is null, distinct from zero. Negative discrepancies are informational, never negative receipts. Count/package units require integers for both quantities. A receipt cannot be edited or deleted; authorized correction users can compensate it once using the existing reversal workflow. Reversal fails atomically if stock is no longer available.

SERIALIZABLE transactions and retry use the existing journal idempotency namespace. The same request returns the original result; a changed request with the same key conflicts. The browser freezes a submitted body/key after an uncertain response and retries it unchanged. Receipts preserve journal history, tenant isolation and ownership. No direct browser database access, hosted fixtures, new dependencies or infrastructure are added.

## Limits

One item per receipt; a delivery containing different items is recorded as separate receipts sharing a reference. No purchase orders, receipt drafts, partial purchase-order fulfillment, batch/serial tracking, individual pallets, transfers or unit conversion. Receiving uses the stock unit, not supplier package conversions. Photos remain disabled hosted. Phase 9 requires separate approval.
