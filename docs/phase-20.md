## Workflow

- Optælling counts one existing item/owner/location balance at a time, including existing zero balances. Pagination/search selects the exact combination. It is the total physical quantity, including identified pallets; it does not silently recount a different owner or location. Previously unregistered combinations must first be registered through the existing inventory workflow.
- Start before physically counting: the server captures quantity, unit, historical names and physical revision. Only one open/count-recorded session can exist for a combination.
- Record a nonnegative decimal string, at most eight decimal places; count/package units require integers. Record and cancel never change inventory. Counts can be corrected while open/count-recorded; version checks prevent overwriting another operator's edit.
- Explicit approval requires counts.approve and inventory.adjust in addition to counts.read/inventory.read. Counts.manage allows start/record/cancel, not approval. This is a permission separation, not a mandatory different-person rule.
- Approval posts the exact difference through the existing immutable correction journal, in the same transaction as closing the count. Zero difference closes without an artificial inventory entry. An approved count remains historical; any later reversal uses the existing inventory journal workflow and is separately audited.
- Any intervening physical change invalidates the count, even an out-and-back movement to the same balance. Cancel, restart and physically recount; neither automatic rebasing nor silent overwrite is allowed. This check applies when recording and approving.
- Reservations and identified pallets remain protected by the existing physical-stock guards. The detail shows current physical/reserved quantities and up to 100 active reservations. Explicitly release affected reservations in Reservationer, or handle shipment-linked reservations through Forsendelser; no automatic release or shipment state change occurs. Reservation-only updates do not invalidate the physical count. A failed approval rolls back both journal and count changes; the same request may succeed after the reservation is explicitly resolved.
- The UI confirms stock-changing approval, explains stale counts, shows actor/reason/time history and retains identical command payloads for retry after uncertain responses.

## Implementation and security

- `app.stock_counts`: owner-managed projection with company-qualified balance/unit/journal links; runtime SELECT only, no direct writes.
- `app.count_events`: immutable authenticated commands, input-only INSERT grants, company/idempotency uniqueness, historical results and actor timestamps set by the private trigger.
- Both tables use RLS requiring the selected company and counts.read/inventory.read. No PUBLIC/anon/authenticated table grants; no runtime execute on private functions.

- Start/record/approve use short row-locking transactions; the API uses existing SERIALIZABLE transactions with bounded whole-transaction retries for serialization/deadlock/idempotency conflicts. No lock is held while an operator counts.
